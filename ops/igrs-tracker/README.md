# IGRS 問い合わせ台帳 + 未返信検知

Gmail の分類と自分の記憶、どちらにも依存しない状態把握のための仕組み。

## なぜ作るか

2026年8月11日の点検で、以下が同時に起きていた。

- web3forms の通知がスパム/ゴミ箱に振り分けられ、5日間気づかなかった（John Sleeman）
- 同一条件の Gmail 検索が、実行のたびに異なる結果を返した（韓国語LPの1件が欠落）
- 検索結果のスレッドが、実際には存在する後続メッセージを含んでいなかった（David Marsh の6通）

いずれも「返信が遅い」問題ではなく「**状況を正しく把握できない**」問題。
案件が20件を超えると、把握そのものが破綻する。

## 対策の3点

1. Gmail 検索は必ず `in:anywhere` — スパム/ゴミ箱を含める
2. スレッドの中身は必ず `getThreadById` で取り直す — 検索結果のスナップショットを信用しない
3. 台帳は Gmail の外（スプレッドシート）に置く — 一覧性を Gmail に依存させない

---

## 前提：既存の売上台帳をそのまま使う

このスクリプトは `IGRS_売上台帳.xlsx` の **`案件台帳` シートの構造に合わせて書かれている**。
新しいシートを作るのではなく、既存台帳に自動化用の列を「追加」する方式。

`案件台帳` の構造（変更しないこと）:

| 行 | 内容 |
|---|---|
| 1 | タイトル |
| 2 | 注記 |
| 3 | 空行 |
| 4 | **ヘッダ** |
| 5〜 | **データ** |

| 列 | 項目 | 誰が埋めるか |
|---|---|---|
| A | 案件ID | 自動（`C001` 形式で採番） |
| B | 受注/問合せ日 | 自動 |
| C | 顧客名 | 自動（フォームの name） |
| D | 連絡先 | 自動（フォームの email） |
| E | 経路 | 自動（`フォーム`） |
| F | LP/国 | 自動（`JA/日本` 形式） |
| G | 内容 | 自動（用途＋必要書類＋期限） |
| H | 見積額 | **手入力** |
| I | 通貨 | 自動で `JPY`、必要に応じて手修正 |
| J | ステータス | **手入力**（`完了`/`失注`/`辞退`/`保留` にすると巡回対象から外れる） |
| K | 備考 | 自動（流入元・traffic_source・LP・本文） |
| L | threadId | 自動 |
| M | 最終更新 | 自動 |
| N | 最終発言者 | 自動 |
| O | 次アクション | **手入力** |
| P | 最終通知 | 自動 |
| Q | 検索キー | 自動（数式） |

A〜K は既存列。**L〜Q は `setupLedger()` が追加する**。
`集計` シートは A・C・H・I・J だけを参照しているので、L 以降を足しても壊れない。

## セットアップ

### 1. スプレッドシートを作る

`IGRS_売上台帳.xlsx` を Google ドライブにアップロードし、
「Google スプレッドシートとして開く」で変換する。

**シート名（`案件台帳` `入金記録` `集計` `ダッシュボード`）は変更しないこと。**
スクリプトがこの名前で参照している。

URL の `/d/` と `/edit` の間がスプレッドシートID。

### 2. Apps Script プロジェクトを作る

スプレッドシートから 拡張機能 → Apps Script。
`Code.gs` の中身を全て貼り付ける。

### 3. スクリプトプロパティを設定

プロジェクトの設定 → スクリプト プロパティ

| プロパティ | 値 |
|---|---|
| `TELEGRAM_TOKEN` | BotFather から取得したトークン |
| `TELEGRAM_CHAT_ID` | 通知先のチャットID |
| `SHEET_ID` | （任意）スプレッドシートID。省略時はバインド先を使用 |
| `OWNER_EMAILS` | （任意）自分のメールアドレス。カンマ区切り。トリガー実行時に `Session.getActiveUser()` が空を返す場合の保険 |

`upwork-fast-lane` と同じ Bot を使い回して構わない。その場合はチャットIDも共通。

### 4. 初期化

エディタ上で、この順に手動実行する。

1. **`setupLedger`** — 自動化列 L〜Q の追加、既存行の検索キー補充、集計・ダッシュボードの容量拡張
2. **`backfillThreadIds`** — 台帳の threadId が空の行を、連絡先から検索して補完
3. **`installTriggers`** — 定期実行を設定

初回実行時に Gmail とスプレッドシートの権限承認を求められる。

`setupLedger` は何度実行しても安全（不足分だけ追加する）。

## 動作

### 15分ごと（`ingestJob`）

`in:anywhere from:web3forms.com newer_than:14d` を走査。
台帳に無いスレッドを見つけたら、フォーム項目をパースして追記し、Telegram に通知。
スパムに振り分けられていても拾う。

`referral_source` と `traffic_source` は備考列に必ず残す。
**AI経由の初受注（C023）はこの項目からしか判明しなかった**ため、集計の一次データとして扱う。

### 2時間ごと（`auditJob`）

台帳の進行中案件を巡回し、20時間以上の未返信を検知して通知。
同一案件の再通知は24時間おき。

**判定は「顧客のメールアドレス宛に、問い合わせ日以降の送信があるか」で行う。**
スレッドの最終発言者では判定しない。返信を元スレッドではなく
案件ごとの新規スレッドで立てる運用のため、元スレッドを見ると
自動通知1通だけが残り「未返信」に誤判定されるから。

連絡先メールも threadId も無い行（LINE・WhatsApp 案件）は自動判定できないため、
巡回では静かにスキップし、日次サマリーの「自動判定なし」枠に出す。

> ingest が15分・audit が2時間なのは意図的。audit は進行中案件1件につき
> Gmail 検索を1回投げるため、15分ごとに回すと案件が増えたときに
> Gmail の実行クォータを圧迫する。警告閾値が20時間である以上、2時間間隔で精度は足りる。

### 毎朝7時（`dailyDigest`）

自分ボール / 相手ボール / 自動判定なし に分けた一覧と、
進行中案件の**見積合計**および**未回収合計**を送信。

見積合計は `入金記録` シートの為替レート表（A6:B10）で円換算してから足す。
台帳の見積額には USD・PHP・GBP 建てが混ざっているため、
単純合計すると 449 USD が 449 円として足されてしまう。

未回収額は `集計` シートの H列（見積(円) − 入金合計(円)）を読む。
着手金を受け取っている案件は総額と残額が食い違うため、両方出す。
（例: トナシロ様 総額78,000円／残39,000円）

**為替レートは仮置きの概算値**（USD 150 等）。実際の着金レートに置き換えること。
確定売上 419,889円 のうち **88,859円はこのレート仮定と、入金日が空欄の
Wise入金3件に依存している**。月別推移を根拠に判断する前に、
Wise の実着金額・着金日を埋めること。

## 台帳の運用

自動で更新されるのは `最終更新` `最終発言者` `最終通知` `検索キー` の4列のみ。
以下は手で埋める。

- **見積額 / 通貨** — 提示した金額。`dailyDigest` の合計に反映される
- **ステータス** — 自由記述。`完了` `失注` `辞退` `保留` のいずれかにすると巡回対象から外れる
- **次アクション** — 通知に表示される。「何をすればいいか」を書いておくと、当直明けに読んで即動ける

`次アクション` を埋めておくかどうかで、この仕組みの価値がほぼ決まる。
「未返信です」だけの通知は、結局スレッドを開き直す手間を生むので。

### 検索キー列（Q列）

`案件ID・顧客名・連絡先・内容・備考` を連結した数式。Ctrl+F での部分一致検索用。
**別名は備考列に併記しておく**とここで拾える。
（例: エコ・シェーン様は WhatsApp 上の表示名が「しい・まり」。
前回この2つを別人と誤判定した。）

## 容量について

`集計` と `ダッシュボード` は元々 `$5:$28` = **24行固定**で、
既存24件でちょうど満杯だった。この状態では新規案件を1件も集計できない。

`setupLedger()` が `LEDGER_CAPACITY`（既定 200件）まで拡張する。
足りなくなったら `Code.gs` 冒頭の `LEDGER_CAPACITY` を上げて `setupLedger()` を再実行する。
容量を超える追記が発生した場合は Telegram に警告が飛ぶ。

## 調整

`Code.gs` 冒頭の定数。

| 定数 | 既定 | 意味 |
|---|---|---|
| `NUDGE_AFTER_HOURS` | 20 | 未返信を警告するまでの時間 |
| `NUDGE_INTERVAL_HOURS` | 24 | 同一案件の再通知間隔 |
| `LOOKBACK_INGEST` | `newer_than:14d` | 新規取り込みの走査範囲 |
| `CLOSED_STATUSES` | 完了/失注/辞退/保留 | 巡回対象から外すステータス |
| `MAX_AUDIT_PER_RUN` | 40 | 1回の巡回で Gmail 検索する上限 |
| `LEDGER_CAPACITY` | 200 | 集計・ダッシュボードが対応する案件数 |

当直で48時間触れない日が出るなら `NUDGE_AFTER_HOURS` を 36 程度に上げた方が、
通知疲れを起こさずに済む。

## Gmail 側の設定（別途、手動）

スクリプトとは独立して、これも入れておく。

設定 → フィルタとブロック中のアドレス → 新しいフィルタを作成

- 条件: `From` に `web3forms.com`
- 動作: **迷惑メールにしない** にチェック、ラベル `問い合わせ` を付ける

web3forms は `notify+1jgbwi@` `notify+sa2oss@` のように毎回異なる送信元を使うため、
個別アドレスではなく**ドメインで指定する**こと。これをしないと Gmail は送信者の信頼度を蓄積できない。

なお、このフィルタが効かなくてもスクリプト側は `in:anywhere` で拾うので、
検知が止まることはない。二重の保険。

## 未対応（LINE / WhatsApp）

**8月の受注4件のうち2件が LINE 経由だが、LINE は一切自動記録されていない。**
現状は手入力しないと台帳から消える。

LINE Messaging API の Webhook を GAS の `doPost` で受ける実装は未着手。
WhatsApp も同様（Whapi.Cloud 経由。医療秘書ボットに稼働実績あり）。

それまでの暫定運用として、LINE/WhatsApp 案件は
`経路` を `LINE` / `WhatsApp` にし、`連絡先` を空のままにしておく。
巡回対象から自動的に外れ、日次サマリーの「自動判定なし」枠に出る。
