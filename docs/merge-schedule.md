## デプロイ頻度の判断基準（波及数 × ローリング7日）

**大原則: 「24時間に1回」は絶対法則ではない。効いているのは時計ではなく「波及ページ数」と「触ったレバー」の2つだけ。**

Googleが再評価するのは `dist/` の静的HTML。判断はソースのファイル数ではなく、**ビルド後にHTMLが変わるページが何枚あるか（＝出力の波及数）**で決める。

- `Footer.tsx` を1ファイル直しただけでも全ページが使っていれば**全ページのHTMLが変わる＝全サイト更新シグナル**。「1ファイルだから安全」は誤り。
- 逆に個別ページ20枚をそれぞれ直しても波及は各ページに閉じる。
- CSS/classNameも同じ。共通コンポーネントの className を変えれば全ページのHTMLが変わる（5/11 grid-cols 65ファイル一括 → +15日で外免切替 -3位の実証）。

### 客観的に測る（推測しない）

`npm run build` 後、`dist/` の `*.html` を main と比較して**変わったHTMLファイル数**を数える＝波及ページ数。< 20 かつ共通コンポーネント/構造レバー非該当なら Level 4・日次OK。20以上 or 共通部品 or 構造なら「大変更」。

> **⚠️ 必ずJSバンドルハッシュを正規化してから数えること（誤測定の最大要因）**
>
> ソースを1行でも変えると vite のバンドル名（`/assets/js/index-XXXXXXXX.js`）が変わり、**全ページのHTMLに1行だけ差分が入ります**。素朴に `cmp` で数えると、実波及1ページの変更が **132ページ**に見えます（#386・2026-08-09 実測）。この誤測定は🟢を🔴に見せるため、判断を根本から狂わせます。過去の #359 で「JSバンドルハッシュ差分131ページは無害ノイズ」と記録されているのと同じ現象です。
>
> 正しい手順（main と対象ブランチの両方をビルドし、`dist_main` を退避してから実行）:
>
> ```python
> import re, pathlib
> pat = re.compile(r'(/assets/(?:js|css)/[A-Za-z0-9._-]*?-)[A-Za-z0-9_-]{8}(\.(?:js|css))')
> norm = lambda p: pat.sub(r'\1HASH\2', p.read_text(encoding='utf-8', errors='replace'))
> base, new = pathlib.Path('dist_main'), pathlib.Path('dist')
> real = [str(f.relative_to(new)) for f in sorted(new.rglob('*.html'))
>         if not (base / f.relative_to(new)).exists() or norm(base / f.relative_to(new)) != norm(f)]
> print('実波及ページ数:', len(real)); [print('  ', r) for r in real]
> ```
>
> シェルの `sed 's|...|...|'` は区切り文字 `|` が正規表現の選択 `(js|css)` と衝突して**黙って失敗し、全ファイルが空になって「波及0」という嘘の結果**を返します。必ず上記のPythonを使うこと。

### ローリング7日バケツ（累積で見る・構造と共通コンポーネントは同じバケツ）

**（2026-07-23 ユーザー承認で14日→7日に短縮）マージ間隔（次の大変更まで空ける日数）は7日に短縮。ただし構造・大量・共通部品の影響がGoogle側で2〜4週間遅れて出る（余震）という実測知見自体は変わらないため、「順位への遅延影響を観察する期間」は引き続き最低14日を推奨する。7日はあくまで次の大きい変更をマージしてよいまでの間隔であり、直前の変更の影響がまだ完全には出きっていない可能性を踏まえた運用判断であることに注意。**

だから危険なのは1回の頻度より**直近7日の累積シグナル量**。**「共通コンポーネント」と「構造ファイル」は別トラックではなく同じ1つのローリング窓を共有する**——構造を入れた3日後に共通コンポーネントを入れる、は「7日以内に2回大きい注ぎ」に該当し禁止。

- **固定バケツではなくスライドするバケツ**: 毎日「今日から遡って7日」を見る。大きい変更前に必ず「過去7日に大きいシグナルを出してないか？」を確認。
- **バケツに入る量は回数ではなく波及の大きさ**: 個別ページ本文＝数滴💧／20ページ超＝大量🪣／共通部品＝一杯／構造＝溢れる＋排水が遅い。
- **ルール**: スライド窓の中に「大きい注ぎ」（構造 or 共通コンポーネント or 20超一括、種類を問わず）は1回まで。数滴（個別コンテンツ）は毎日足しても溢れない。

### デプロイ確認の落とし穴（2026-08-09 調査で判明）

- **Cloudflare Pages のデプロイは GitHub Actions には出ない（Checks には出る）**。`.github/workflows/` にあるのは `gsc-monitor.yml`・`hreflang-check.yml`・`seo-gate.yml` の3つだけで、サイトのデプロイは Cloudflare の Git 連携が push を検知して自前でビルドしている。ただし Cloudflare Pages の GitHub App は **`Cloudflare Pages` という名前の check run** を出すため、**Actionsタブではなく Checks（PRのチェック一覧）を見ること**。PRではプレビューデプロイの成否がここで確認でき、BotがプレビューURL付きのコメントも残す（#413 で実測）。ビルドログ本体は Cloudflare ダッシュボード（check run の details_url）にある。
- **`hreflang Post-Deploy Check` の緑チェックは「hreflang が正常」の証明にならない**。`hreflang-check.yml` の検証ステップに `continue-on-error: true` が付いているため、**hreflang が全削除されていてもジョブは success で終わり**、メール通知が飛ぶだけ。Actions一覧の ✅ は「デプロイが完了した」ことしか意味しない。実際の合否は **ジョブのステップ単位**（`Run hreflang check` の conclusion と `Send alert if hreflang broken` が skipped か）で確認するか、`python scripts/check_hreflang.py` を手元から本番に対して実行して確かめること。
- **マージ前フックの文言が古い**。フックは「ローリング**14日**バケツ」と表示するが、#378（2026-07-25・ユーザー承認）で**7日**に短縮済み。正典は本ファイルと CLAUDE.md であり、フックの表示ではない。
- **docs のみのPRでも Cloudflare のビルドは毎回走る**（ビルド出力は変わらないためGoogleへの更新シグナルにはならない）。2026-08-08 は12分間に5回 push され、ビルドも5本連続で走った。CLAUDE.md の「デプロイは1日1回まで」からの逸脱にあたるため、**docs 更新は複数件をまとめて1回の push にすること**。
