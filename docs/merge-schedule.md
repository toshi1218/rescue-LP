# PR マージスケジュール

最終更新: 2026-07-02（PR棚卸し・確定デプロイカレンダー反映）

> **判定基準**（CLAUDE.md「運用の大原則」準拠）
> - 🟢 **安全**: 構造ファイル無変更・20ファイル未満・共通コンポーネント連打なし → 個別ページ爆発半径・日次OK
> - 🟡 **要観察**: 共通コンポーネント（Navbar等）に触れる or prerender/sitemap に追記 → 単独・14日観察
> - 🔴 **マージ不可**: 20ファイル超の一括 or 構造＋共通コンポーネント → 分割が必要
>
> 構造ファイル = prerender.ts / useMeta.ts / urlMap.ts / sitemap.xml / robots.txt / _redirects / seoDate.ts / hreflang / canonical

## デプロイ頻度の判断基準（波及数 × ローリング2週間）

**大原則: 「24時間に1回」は絶対法則ではない。効いているのは時計ではなく「波及ページ数」と「触ったレバー」の2つだけ。**

Googleが再評価するのは `dist/` の静的HTML。判断はソースのファイル数ではなく、**ビルド後にHTMLが変わるページが何枚あるか（＝出力の波及数）**で決める。

- `Footer.tsx` を1ファイル直しただけでも全ページが使っていれば**全ページのHTMLが変わる＝全サイト更新シグナル**。「1ファイルだから安全」は誤り。
- 逆に個別ページ20枚をそれぞれ直しても波及は各ページに閉じる。
- CSS/classNameも同じ。共通コンポーネントの className を変えれば全ページのHTMLが変わる（5/11 grid-cols 65ファイル一括 → +15日で外免切替 -3位の実証）。

### レバー × 波及数 → 頻度

| 触るレバー | 波及ページ | 同日の頻度 | 観察 |
|-----------|-----------|-----------|------|
| **Level 4・個別ページ**（本文・新規ページ・内部リンク・画像/alt・1ページ限定のUI/CSS） | 1〜数 | **1日2回OK**（合計20ページ未満・同じ共通部品を連打しない） | 不要 |
| **Level 4だが大量**（20ページ以上を一括） | 20+ | 1日1回・バースト禁止 | 14日 |
| **Level 3**（title・H1・meta description・グローバルナビリンク） | 1〜2推奨 | 1日1回・1〜2ページまで | **2週間**空けて次 |
| **共通コンポーネント**（Header/Footer/Hero/Nav/Pricing/WhyUs/FAQ/CardGrid 等）※ファイル数不問 | **全ページ** | 1回入れたら止める | **14日**・その窓で他の共通部品を出さない |
| **構造**（hreflang/canonical/sitemap/robots/_redirects/URL/ドメイン/prerenderルート/useMeta/urlMap/seoDate/JSON-LD） | **全サイト＋遅延余震** | 単独で1回・他と絶対混ぜない | **14〜28日**・他の構造変更を凍結 |

### 客観的に測る（推測しない）

`npm run build` 後、`dist/` の `*.html` を main と比較して**変わったHTMLファイル数**を数える＝波及ページ数。< 20 かつ共通コンポーネント/構造レバー非該当なら Level 4・日次OK。20以上 or 共通部品 or 構造なら「大変更」。

### ローリング2週間バケツ（累積で見る）

構造・大量・共通部品の影響は2〜4週間遅れて出る（余震）。だから危険なのは1回の頻度より**直近14日の累積シグナル量**。

- **固定バケツではなくスライドするバケツ**: 毎日「今日から遡って14日」を見る。大きい変更前に必ず「過去14日に大きいシグナルを出してないか？」を確認。
- **バケツに入る量は回数ではなく波及の大きさ**: 個別ページ本文＝数滴💧／20ページ超＝大量🪣／共通部品＝一杯／構造＝溢れる＋排水が遅い。
- **ルール**: スライド窓の中に「大きい注ぎ」は1回まで。数滴（個別コンテンツ）は毎日足しても溢れない。共通部品・構造を14日以内に2回やると溢れる＝「1回入れたら14日空ける」。

## 残りスケジュール（🟡🔴・期日が来たら session-start フックが通知）
