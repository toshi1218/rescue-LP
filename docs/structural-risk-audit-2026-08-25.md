## 0. 検討していたリニューアル案と結論

ユーザー案:

1. 違うURLでホームページを1から作る
2. 今のURLを301で新しく作ったページに飛ばす
3. ドメインはそのままに中身は一新される

**結論: 1と2は不採用。3のみ実施する。**

理由:

- 「中身の一新」（デザイン・コード・文章・内部リンク・構造化データ）は **URLを1本も変えずに100%達成できる**。`prerender.ts` を持っている以上、URL文字列と中身の対応は完全に自由。
- URL変更が持ち込むSEO上のプラスはほぼゼロ（URL内キーワードはランキング要因としてほぼ死んでいる）。
- 一方でコストは最大:
  - **301が2段になる**。このサイトは既に1回URL移行済み（`/cenomar/ → /en/cenomar/` 等が `public/_redirects` に205ルール生存）。もう一度移すと2ホップのチェーンになる。
  - **hreflang を 127URL × 3言語ぶん全張り替え**になる。相互参照が1本でも崩れると言語グループ全体の判定が保留される。3/29のhreflang全削除事故が全ページ規模で再現するリスク。
  - **クロールバジェットが足りない**。Googleインデックスは約35件（Bing 99件）と少ない。新URL127本の再評価完了まで数ヶ月かかる。
  - **生存中の資産を全部賭ける**ことになる（`/ja/psa-shussei-cost/` 順位1.24、NBI系、外免切替クラスター）。
- 「評価を捨てて心機一転」が目的なら301では実現しない。301は評価を*引き継ぐ*仕組みであり、目的と手段が逆。

個別のURLに不満がある場合は、**1〜2本ずつ**個別対応する。127本まとめてやる理由にはならない。

## 2. 実在する構造的リスク（重い順）

### 🔴 リスク1. 鮮度シグナルが約5ヶ月止まっている

監査日は8月25日。しかしビルド出力の実測は以下:

- **76ページの `<title>` に「[April 2026]」「2026年4月」が焼き込まれている**（`/en/`、`/en/nbi-clearance/`、`/en/uae/` ほか）
- **sitemap の `lastmod` は 127本中 104本が `2026-04-01`**
- `lib/seoDate.ts` の `SEO_MONTH = '4'` が、このファイルが導入された **2026-07-28 以降ずっと '4' のまま**。ファイル自身のヘッダーに「月1回このファイルだけ更新すればサイト全体に反映されます」と書いてあるが、その運用は一度も回っていない
- さらに **`2026年3月` 等の古い日付がリテラル直書きされたファイルが64枚**あり、定数を迂回している。`seoDate.ts` を更新してもこれらは古いまま残る

検索結果に「【2026年4月最新】」と出ているのを8月末のユーザーが見た場合、それは鮮度アピールではなく「放置されたサイト」という表示になる。順位以前にCTRと信頼を毀損する。
問い合わせの76%がChatGPT経由というLLMO文脈でも、日付が古い情報はLLMが引用を避ける要素になる。

**構造を触らずに直せる。単なる運用漏れ。**

### 🔴 リスク2. noindex ページに向かって hreflang が張られている（3件）

```
/ja/kekkaku-shomeisho/       --hreflang=en--> /en/tb-certificate/                   (noindex・sitemap未掲載)
/ja/kokusai-kekkon-roadmap/  --hreflang=en--> /en/personalized-roadmap/             (noindex・sitemap未掲載)
/ja/kojin-joho-hogo/         --hreflang=en--> /en/personal-information-protection/  (noindex・sitemap未掲載)
```

**`x-default` も同じ noindex ページを指している。**

Googleの仕様では noindex ページは hreflang クラスタから除外される。結果としてこの3つの日本語ページ（いずれも indexable）の hreflang はクラスタごと無効化されている可能性が高い。x-default が実質死んだURLを指しているのが特に悪く、言語判定そのものが不能になる。

原因は `scripts/prerender.ts` の `getHreflangMode()` に「alternate が noindex なら hreflang を出さない」という判定が**無い**こと。ロジック数行の話で、影響は3ページ限定。

### 🟠 リスク3. メタ情報が二重管理（設計上の欠陥・放置すると永久に再発）

- `pages/*.tsx` 126枚中 **116枚が `useMeta()` を呼び、hydration後に title/description を上書き**している
- `scripts/prerender.ts` が静的HTMLに焼く title とは**別ソース**
- 機械比較で **少なくとも28ページが文字列不一致**

Googleは静的HTML（1パス目）とJS実行後（2パス目）の両方を見るため、どちらが採用されるか不定 = snippetが不安定になる。

問題は件数ではなく構造。**二重ソースである限り必ずまた乖離する。**
CLAUDE.md の「持ち越しタスク A: 残り84ページの同期修正を5〜10ページずつ複数セッションで」は、対症療法を10セッション以上続ける計画であり、根治しない限り終わらない。

### 🟠 リスク4. `scripts/prerender.ts` 2142行への一極集中 ←「構造を触るのが怖い」の正体

このファイル1本が、**125ルート分の path / title / description / canonical / hreflang / lastmod / JSON-LD を全て**抱えている。

- 1ヶ所の typo で全ページのビルドが落ちる
- 1行の変更が全ページのHTMLを書き換えうる
- `lastmod` は125ルート中 **23本だけ手書き**、残り102本は定数任せで実態と乖離

CLAUDE.md が「構造ファイルは永久に触るな」と言わざるを得ないのは、**触ると必ず全ページに波及する作りだから**。爆発半径がコード構造によって強制されている。

**リニューアルで直す価値がある唯一の項目がこれ（とリスク3）。**

### 🟡 リスク5. その他（実害小・把握のみ）

- **hreflang の無いページが34枚**。`/en/saudi-arabia/` 等の国別ページ、`/ja/business/` 配下、`/en/k1-visa-documents/` など。相手言語のページが無いための正しい挙動でありバグではない。
  ただし `/en/k1-visa-documents/` と `/en/cr1-visa-documents/` は `lib/urlMap.ts` で3本とも `/ja/us-visa-documents/` を指す**多対1マッピング**のため相互参照が成立せず hreflang が出ていない。害はないが言語クラスタが痩せている。
- **JS 合計 2.3MB / 156ファイル、初期バンドル 306KB（gzip 90KB）、HTML 84〜116KB/ページ**。prerender済みなので初回表示は速いが、hydrationコストは INP（Core Web Vitals）に効く。致命的ではない。
- **contact 3ページの CLS**: `components/Footer.tsx` の `isContactPage` 判定が `typeof window !== 'undefined'` ガードの中にあるため、prerender時は常に `false`。静的HTMLにはフッターのフォームが入ったまま出力され、hydration後に `hidden` で消える。表示直後にフォームが消えるレイアウトシフトが発生する。

### リニューアルとの対応関係

| リスク | リニューアルが必要か |
|---|---|
| 1. 日付5ヶ月停止 | **不要**。定数更新＋リテラル撲滅で直る |
| 2. noindexへのhreflang | **不要**。`getHreflangMode()` に判定を足すだけ |
| 3. メタ二重管理 | **書き直す価値あり**。ページごと1ファイルの単一ソースにし、prerenderとuseMetaが同じものを読む設計にすれば永久に再発しない |

| 5. バンドル・URL | URL変更は不要かつ有害（第0節） |

**リニューアルの正当な理由はリスク3と4のみで、どちらもURLを1本も変えずに達成できる。**

## 5. `lastUpdated` の正しい直し方（重要）

`components/HeroBanner.tsx` の `lastUpdated` プロップは `Updated: 2026年3月1日` として画面に表示される、**ユーザーに対する事実の主張**である。

**内容を更新していないのに更新日だけ新しくするのは虚偽表示であり、やってはいけない。**

代わりに機械的に正しい方法がある: **表示値と git 上の実際の最終変更日を突き合わせ、表示のほうが古い（＝表示が事実として間違っている）ものだけを、実際の日付に訂正する。**

### ただし履歴が 2026-07-28 で squash されている

`git rev-list --max-parents=0 HEAD` = `dea3f93`（2026-07-28、362ファイル・49925行の追加）。
つまり **7/28 より前の履歴はこのリポジトリに存在しない**。多数のファイルが「最終変更 2026-07-28」と出るが、これは root commit の日付であって実際の更新日ではない。

→ **検証可能なのは root 以降に実際に変更された13ファイルのみ**。残る約30枚の `2026年3月1日` は真の更新日が不明なため、**推測で動かさず据え置く**。
